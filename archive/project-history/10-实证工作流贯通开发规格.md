## 1. 背景与问题定义

ResearchPath 已完成入口重构：首屏区分“规划新研究”和“分析已有数据”，已有数据按时间结构、依赖结构和研究设计三个正交维度组织。项目上下文与数据结构角色已经可以保存，嵌套、面板和密集追踪数据在角色未确认时不能进入后续流程。

当前主要问题不再是“缺少入口”，而是同一个研究事实仍需在多个工作台重复声明：

- 数据准备已经指定 subject、cluster、time，纵向、多层或 ESM 配置仍需再次选择；
- 测量版本、分析样本和结构角色分别存在，但下游规格没有统一解析后的上下文；
- MI 已绑定线性回归核心模型，但插补产物还不是其他分析工作流的正式输入；
- 高级测量可运行，但没有完全按横截面、嵌套、纵向和密集追踪语义拆分准备步骤；
- 规划新研究目前主要提供功效工具，还没有形成能复用到数据分析阶段的计划对象。

本规格不新增统计方法，优先贯通所有当前支持能力。

## 2. 目标与非目标

### 2.1 产品目标

1. 用户只声明一次研究结构和核心变量角色。
2. 系统把已确认角色自动传入适用方法，并允许用户在分析规格中显式覆盖。
3. 所有运行都绑定同一组可追溯身份：数据版本、结构版本、测量版本、分析样本、插补版本、模型规格和随机种子。
4. 结构或上游对象发生变化时，下游配置明确失效，不静默沿用。
5. 方法目录只显示当前上下文真正适用且可执行的切片。
6. 规划阶段生成的研究计划能成为分析阶段的默认配置来源，而不是孤立文档。

### 2.2 工程目标

1. 建立统一的 `ResolvedAnalysisContext`，消除各工作台自行推断变量角色。
2. 建立方法需求注册表，服务端作为适用性和缺失前置条件的唯一事实来源。
3. 建立显式 lineage 与 invalidation 规则。
4. 保持 JSON Schema、Python、OpenAPI、TypeScript 和 R 输入同步。
5. 不提高类型、覆盖率、统计容差、bundle 或性能门槛来掩盖问题。

### 2.3 非目标

- 不在本轮新增三层模型、任意交叉分类、连续时间模型、潜变量 DSEM 或通用广义多层中介。
- 不把通用 MI 宣称为支持任意下游模型的自动合并。
- 不建设云端账户、协作、同步或远程任务。
- 不恢复 `archive/` 中未接线的历史原型。
- 不让前端根据组件是否存在来猜测方法是否可执行。

## 4. 核心领域模型

### 4.1 AS-IS 对象

- `StudyContextRecord`：项目级时间结构、依赖结构和研究设计，带 revision。
- `DatasetStructureRecord`：数据版本上的 subject、cluster、time 角色，带 revision。
- `DatasetVersion`：不可变数据与来源身份。
- `MeasurementVersion`：构念、题项方向、计分及派生变量。
- `AnalysisSampleReference`：显式质检样本版本，或由 dataset SHA 确定的虚拟全案例样本引用。
- `ModelSpec / AdvancedAnalysisSpec`：具体分析规格。
- `ResultBundle / AdvancedResultBundle`：结果、警告、执行方法和 provenance。

### 4.2 新增 `ResolvedAnalysisContext`

服务端应在运行前统一解析以下对象：

```json
{
  "schemaVersion": "1.0.0",
  "projectId": "default",
  "dataset": {
    "id": "dataset_...",
    "hash": "...",
    "sha256": "..."
  },
  "studyContext": {
    "id": "context_...",
    "hash": "...",
    "revision": 3,
    "value": {
      "timeStructure": "single_occasion",
      "dependencyStructure": "nested",
      "designType": "observational"
    }
  },
  "structure": {
    "id": "structure_...",
    "hash": "...",
    "revision": 2,
    "roles": {
      "subjectId": "person_id",
      "clusterId": "team_id",
      "timeId": null
    },
    "status": "valid"
  },
  "measurement": {
    "id": "measurement_...",
    "hash": "..."
  },
  "sample": {
    "id": "sample_all_ab12cd34",
    "hash": "..."
  },
  "imputation": null,
  "contextHash": "...",
  "validity": "ready",
  "missingRequirements": [],
  "warnings": [],
  "validFor": ["cross_sectional_nested"]
}
```

设计要求：

- `ResolvedAnalysisContext` 是服务端生成的只读视图，不由前端拼接。
- 没有选择测量、样本或插补版本时字段可为空，但运行器需求注册表决定是否允许为空。
- hash 使用规范化 JSON 或已有对象内容哈希，不能使用显示标签。
- 每个任务状态与结果 provenance 保存完整解析上下文或其不可变引用。

### 4.3 结构角色语义

| 角色 | 语义 | 最低校验 |
| --- | --- | --- |
| `subjectId` | 个体或主要研究对象 | 非缺失率、重复模式、与时间键联合唯一性 |
| `clusterId` | Level 2 聚类单位 | cluster 数、最小/中位/最大组规模、单例组 |
| `timeId` | 波次、时间戳或测量序列 | 可排序、个体内重复、重复时间键和间隔分布 |
| `groupId` | 比较或处理分组 | 水平数、空单元、极小组；不得自动等同 cluster |
| `treatmentId` | 实验/准实验处理 | 处理水平、分配结构、基线与缺失 |
| `weightId` | 抽样或分析权重 | 正值、极端权重、当前方法是否支持 |

本轮 P0 至少新增 `groupId` 与 `treatmentId`。`weightId` 只有在存在支持权重的执行切片后才进入活动契约。

### 4.4 角色来源与覆盖优先级

从高到低：

1. 当前分析规格中的显式覆盖；
2. 数据版本的已确认结构角色；
3. 研究计划中冻结的默认角色语义；
4. 系统建议候选。

系统建议只能预填，不能直接成为正式运行角色。发生覆盖时，规格必须记录 `roleOverrides` 及理由；不允许静默替换。

## 5. 方法需求注册表

### 5.1 目标

把“是否适用、缺什么、默认带入什么”从 React 条件分支移到后端注册表。每个可执行 slice 增加：

```json
{
  "sliceId": "cross_sectional_two_level_gaussian",
  "compatibleTimeStructures": ["cross_sectional"],
  "compatibleDependenceStructures": ["nested"],
  "compatibleDesigns": ["observational", "randomized", "quasi_experimental"],
  "requiredRoles": ["clusterId"],
  "optionalRoles": ["subjectId"],
  "requiredArtifacts": ["datasetVersion"],
  "acceptedImputationTargets": ["none"],
  "executionAvailable": true
}
```

### 5.2 适用性响应

能力发现响应增加：

- `applicable`：当前上下文是否适用；
- `missingRequirements`：缺失角色或对象；
- `defaultBindings`：可自动带入的角色；
- `blockedReason`：统计边界说明；
- `requiresRevalidation`：上游变化后是否失效。

前端只展示服务端返回的适用能力。`executionAvailable=true` 仍是全局门槛，`applicable=true` 是当前研究上下文门槛，两者缺一不可。

## 6. 数据结构准备与自动传递

### 6.1 结构确认页面

保存前执行结构画像：

- 横截面嵌套：cluster 数、组规模、单例组、缺失 cluster；
- 面板：subject×time 联合重复、波次数、个体波次分布、间隔；
- 密集追踪：时间排序、重复时间戳、个体观测数、预期间隔偏离；
- 额外嵌套：subject 与 cluster 的包含关系，识别三层或交叉分类风险。

保存响应返回 `status = valid | warning | invalid`。warning 允许带理由继续，invalid 不允许进入下游。

### 6.2 自动预填

- `MultilevelWizard.clusterVariableId ← roles.clusterId`
- 纵向规格 `subjectId ← roles.subjectId`
- 纵向波次/长格式设置 `timeId ← roles.timeId`
- 日记/ESM `personId ← roles.subjectId`、`timeVariableId ← roles.timeId`
- 重复测量实验 `subjectId ← roles.subjectId`
- cluster-robust 实验 `clusterId ← roles.clusterId`
- 多层 MI `clusterVariableId ← roles.clusterId`

自动预填发生在创建新草稿时。已保存草稿不能被后台角色变化直接改写，而应标记失效并要求用户确认迁移。

### 6.3 上游变更失效规则

| 变化 | 必须失效的对象 |
| --- | --- |
| 时间结构变化 | 结构确认、纵向/ESM/实验重复测量规格、相关结果 |
| 依赖结构变化 | cluster 确认、多层/聚合规格、忽略依赖的普通回归推荐 |
| subject/time/cluster 角色变化 | 所有引用对应角色的草稿、运行和派生结果 |
| 数据版本变化 | measurement、sample、imputation、model、result 的旧默认选择 |
| measurement 变化 | 使用构念分数或题项结构的分析 |
| sample 变化 | MI、模型和结果 |
| 核心分析模型变化 | 对应 MI 计划与插补版本 |

历史结果不删除，状态改为 `superseded` 或显示“基于旧上游版本”，且保留原 provenance。

## 7. MI 与下游分析串联

### 7.1 当前边界

当前通用 MI 正式支持：类型感知 MICE、显式线性回归核心模型、Rubin 合并和相关诊断。`substantiveModelHash` 已能发现核心模型变化。

### 7.2 目标对象

新增不可变 `ImputationPlanVersion` 与 `ImputationDatasetVersion`：

```text
DatasetVersion
  └─ AnalysisSampleReference
       └─ ImputationPlanVersion
            ├─ substantiveModelHash
            ├─ structureHash
            ├─ predictorMatrixHash
            └─ ImputationDatasetVersion
                 └─ pooled analysis result
```

`ImputationPlanVersion` 至少绑定：

- dataset SHA；
- sample hash；
- structure hash；
- measurement hash（使用构念分数时）；
- 核心分析模型类型与 hash；
- 插补变量、预测矩阵、被动规则；
- cluster 角色（两层 MI 时）；
- m、iterations、seed 和诊断。

### 7.3 下游连接策略

1. P1 继续只允许 `linear_regression` 正式 Rubin 合并。
2. UI 中已生成的插补版本只能被相同 `substantiveModelHash` 的分析选择。
3. 模型不一致时返回 `MI_SUBSTANTIVE_MODEL_CHANGED_REIMPUTE_REQUIRED`。
4. SEM、PROCESS 和横截面多层模型在没有正式 pooled runner 前，只能显示“不支持消费该通用插补版本”，不能拿单一插补数据替代 Rubin 推断。
5. 日记/ESM 自有二层 MI 保持独立切片，不与通用 MI 混用。

### 7.4 结果与导出

结果必须包含：

- `imputationPlanVersionId`；
- `imputationDatasetVersionId`；
- `substantiveModelHash`；
- m、迭代、失败链、实际方法；
- Rubin 分解、FMI、自由度与诊断；
- 数据、样本、结构和测量 lineage。

## 8. 结构专属测量准备

### 8.1 横截面独立

- 题项类型、反向题与构念计分；
- α、ω、EFA/CFA、CR、AVE、HTMT；
- 高级 ESEM、Bifactor、GRM IRT/DIF 与 CMB 诊断。

### 8.2 横截面嵌套

- 保留个体层测量证据；
- cluster 角色自动进入 ICC 与聚合诊断；
- 明确区分“题项/构念聚合证据”和“多层测量模型”；
- 当前没有多层 CFA 时不得显示为已支持。

### 8.3 面板

- 测量时点映射使用已确认 subject/time；
- 纵向 configural/metric/scalar/strict 等值性；
- 部分等值释放记录到规格；
- 未满足可比性时限制潜均值或结构路径解释，不自动删除模型结果。

### 8.4 密集追踪

- 构念的 within-person 与 between-person 信度；
- 个体内变异不足检查；
- 测量时点与依从性诊断；
- 不把横截面 α 单独作为 ESM 测量质量结论。

## 9. 规划新研究工作台

### 9.1 目标对象 `StudyPlanVersion`

规划工作台应保存而非只展示表单：

- 研究问题与 estimand；
- 时间、依赖和设计结构；
- 计划角色及变量语义；
- 构念、题项、测量时点；
- 抽样单位、cluster、波次/测量次数；
- 主分析方法与稳健性分析；
- 缺失数据策略；
- 功效、精度或 MDES 规格；
- 假设、版本、冻结状态和偏离说明。

### 9.2 从计划到数据

导入数据后提供显式映射：

```text
计划角色/构念 → 实际变量 → 映射状态 → 偏离说明
```

计划只能提供默认值，不能绕过数据画像和人工确认。冻结计划与实际分析不同的字段进入 deviation 记录。

### 9.3 规划阶段可用工具

- 通用功效、精度与 MDES；
- 回归、t 检验、ANOVA 和登记的 Monte Carlo 功效；
- 面板与 ESM 已有专属功效切片，在计划结构匹配时呈现；
- 尚未支持的分析不能用近似功效工具冒充精确设计。

## 22. 规范化与 hash 算法

### 22.1 Canonical JSON

新增 `apps/api/app/services/canonical_identity.py`，只提供纯函数：

```python
def canonical_json(value: object) -> bytes:
    return json.dumps(
        value,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
        allow_nan=False,
    ).encode("utf-8")

def canonical_sha256(value: object) -> str:
    return hashlib.sha256(canonical_json(value)).hexdigest()
```

要求：

- Pydantic 对象先用 `model_dump(mode="json", by_alias=True, exclude_none=False)`；
- datetime 一律 UTC ISO-8601，写入前转换，hash payload 中不包含 `createdAt/updatedAt/revision`；
- list 保持业务顺序；只有语义定义为集合的字段在 contract validator 中先排序；
- 浮点值不允许 NaN/Infinity；
- hash 输入必须在测试中保存明确 payload，不能只断言长度为 64。

### 22.2 各对象 hash payload

| hash | 必含字段 | 明确排除 |
| --- | --- | --- |
| `studyContextHash` | schemaVersion、timeStructure、dependenceStructure、design | projectId、revision、时间戳 |
| `structureHash` | datasetVersionId、contextSnapshot、roles、profileStatus、overrideReason | id、revision、时间戳 |
| `analysisContextHash` | dataset SHA、studyContextHash、structureHash、measurementHash、sampleHash、imputation hash | UI 标签、更新时间 |
| `substantiveModelHash` | modelType、outcomeId、predictorIds、includeIntercept | analysisId、名称、seed |
| `imputationPlanHash` | context hashes、变量/方法、预测矩阵、被动规则、m、iterations、seed、substantiveModelHash | 任务 ID、结果路径 |

## 23. 精确领域契约

以下字段名使用跨语言 camelCase。Python 使用 alias 映射，SQLite 使用 snake_case。

### 23.1 `StudyContextVersion`

```typescript
interface StudyContextVersion {
  schemaVersion: '1.0.0'
  id: string                    // context_<32 lowercase hex>
  projectId: string             // 当前固定 default；保留扩展
  revision: number              // 同 project 从 1 连续递增
  timeStructure: 'cross_sectional' | 'panel' | 'intensive_longitudinal'
  dependenceStructure: 'independent' | 'nested'
  design: 'observational' | 'randomized' | 'quasi_experimental'
  contextHash: string           // 64 位小写 SHA-256
  createdAt: string             // UTC ISO-8601
}
```

### 23.2 `DatasetStructureVersion`

```typescript
type StructureStatus = 'valid' | 'warning' | 'invalid'

interface DatasetRoleBindings {
  subjectId: string | null
  clusterId: string | null
  timeId: string | null
  groupId: string | null
  treatmentId: string | null
}

interface StructureProfile {
  rowCount: number
  missingRoleCounts: Record<string, number>
  duplicateSubjectTimeCount: number | null
  subjectCount: number | null
  clusterCount: number | null
  singletonClusterCount: number | null
  clusterSize: { minimum: number; median: number; maximum: number } | null
  observationsPerSubject: { minimum: number; median: number; maximum: number } | null
  timePointCount: number | null
  nestingClassification: 'none' | 'two_level' | 'three_level' | 'cross_classified' | 'ambiguous'
}

interface DatasetStructureVersion {
  schemaVersion: '1.0.0'
  id: string                    // structure_<32 lowercase hex>
  datasetVersionId: string
  projectId: string
  revision: number
  studyContextVersionId: string
  contextSnapshot: StudyContextInput
  roles: DatasetRoleBindings
  profile: StructureProfile
  status: StructureStatus
  warnings: Array<{ code: string; severity: 'warning' | 'error'; message: string }>
  overrideReason: string | null // status=warning 时继续必须填写，10..1000 字
  structureHash: string
  createdAt: string
}
```

校验：

- panel/ESM 必须有 subjectId、timeId；nested 必须有 clusterId；
- 所有非空角色必须是 dataset 中已知 variable id；
- subject、cluster、time 三者必须不同；group/treatment 可相同，但 UI 必须明确用户意图；
- panel/ESM 的 `(subjectId,timeId)` 重复使 status=invalid；
- nested 且 clusterCount < 2 使 status=invalid；
- nested 且 clusterCount < 20 或存在单例组使 status=warning；阈值只触发警告，不自动改变估计器；
- `three_level/cross_classified/ambiguous` 对普通两层 slice 返回 not applicable；
- warning 保存必须提供 overrideReason；invalid 不可保存为当前有效结构。

### 23.3 `ResolvedAnalysisContext`

```typescript
interface ResolvedArtifactRef {
  id: string
  hash: string
}

interface ResolvedAnalysisContext {
  schemaVersion: '1.0.0'
  projectId: string
  dataset: ResolvedArtifactRef & { sha256: string }
  studyContext: ResolvedArtifactRef & { revision: number; value: StudyContextInput }
  structure: ResolvedArtifactRef & {
    revision: number
    roles: DatasetRoleBindings
    status: 'valid' | 'warning'
  }
  measurement: ResolvedArtifactRef | null
  sample: ResolvedArtifactRef       // 显式 sample version 或确定性 all-cases ref
  imputation: ResolvedArtifactRef | null
  contextHash: string
  validity: 'ready' | 'incomplete' | 'stale'
  missingRequirements: string[]
  warnings: Array<{ code: string; severity: 'info' | 'warning'; message: string }>
}
```

解析失败不是 404：只要 dataset 存在就返回 200 和 `validity=incomplete`；dataset 不存在才返回 404。

## 25. API 精确协议

所有 mutation 继续要求 `X-ResearchPath-Token`。错误使用 FastAPI detail 对象：

### 25.1 项目上下文

`PUT /api/v1/projects/{projectId}/study-context`

```json
{
  "expectedRevision": 2,
  "context": {
    "schemaVersion": "1.0.0",
    "timeStructure": "panel",
    "dependenceStructure": "independent",
    "design": "observational"
  }
}
```

- 首次写入 `expectedRevision=null`；
- revision 不匹配返回 409 `REVISION_CONFLICT`；
- 与“最新版本”相同的 contextHash 幂等返回最新版本，不新增 revision；A→B→A 必须产生第三个 revision，不能返回已非当前值的 revision 1；
- GET 返回最新 `StudyContextVersion`；
- `GET .../versions` 返回按 revision 降序列表。

兼容期继续接受当前未包裹的 `StudyContextInput` body，按“读取最新 revision 后新增版本”处理，并在响应 warning/header 标记 deprecated；新前端必须使用带 expectedRevision 的 body。

`POST /api/v1/datasets/{datasetId}/study-structure/validate`

- imputation 省略：null；

## 28. 状态机与失效算法

### 28.1 草稿状态机

```text
create
  ├─ requirements missing ─→ incomplete
  └─ requirements complete ─→ ready

ready/incomplete
  ├─ same context edit ─→ ready|incomplete (revision + 1)
  ├─ upstream hash changed ─→ stale
  └─ user creates replacement ─→ superseded

stale
  ├─ migrate and confirm ─→ new ready draft; old remains superseded
  └─ no action ─→ readable, never runnable
```

禁止把 stale 草稿原地改回 ready；迁移产生新 draft ID，保证旧运行可追踪。

### 28.2 运行门禁顺序

1. dataset 存在且 SHA 与 snapshot 一致；
2. structure、measurement、sample、imputation 身份属于 dataset；
3. current contextHash 与 draft contextHash 一致；
4. capability `executionAvailable && applicable`；
5. requiredRoles/Artifacts 完整；
6. role override 合法且有理由；
7. family contract 通过；
8. slice contract 通过；
9. 资源预算通过；
10. 创建任务并保存 context snapshot ID。

任何失败都不得创建 job 行或结果目录。

### 28.3 Invalidation 伪代码

```python
for draft in repository.list_active_drafts(dataset_id):
    if draft.context_hash != new_context.context_hash:
        repository.mark_draft_stale(draft.id, diff_contexts(draft, new_context))

for result in repository.list_results(dataset_id):
    if result.context_hash != new_context.context_hash:
        repository.record_invalidation(
            analysis_id=result.id,
            reason="ANALYSIS_CONTEXT_CHANGED",
            previous_hash=result.context_hash,
            current_hash=new_context.context_hash,
        )
```

同一 invalidation 以 `(analysis_id, reason, current_hash)` 唯一，重复计算必须幂等。

## 32. 切换、回滚与恢复步骤

### 32.1 功能切换顺序

1. migration 与新 API 先上线，旧前端仍能使用兼容接口；
2. 新前端读取 resolved context/applicability；
3. 各向导逐个改用 draft adapter；
4. 全部消费者完成后删除前端硬编码路由判断；
5. P1 结束后停止前端调用旧 `PUT /study-structure`；
6. 旧数据库表至少保留一个发布周期，不在本轮删除。

### 32.2 失败回滚

- migration 失败：SQLite 事务回滚，程序拒绝启动并保留原数据库；
- 新 API 失败：旧数据未改变，前端显示阻塞，不回退到本地猜测；
- 向导 adapter 失败：不保存草稿、不创建 job；
- R 运行失败：任务 failed，保留 plan/context identity 和原始诊断；
- Full 失败：不得合并；修复根因，不修改门槛。

### 32.3 备份恢复验收

workspace archive 必须包含新表与下列受控文件：

- context snapshot；
- imputation manifest/artifacts；
- study plan payload；
- draft spec；
- invalidation records。

恢复演练后执行 database quick check、foreign key check、对象 hash 校验和至少一个历史结果读取。

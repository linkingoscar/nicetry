# 24 工程 Harness 与开发准则

> 文档版本：2.1.0
> 形成日期：2026-07-15
> 最近修订：2026-07-22
> 适用对象：ResearchPath 开发者、审阅者、CI 和自动化代理
> 机器入口：`scripts/harness.ps1`
> 机器可读工程地图：`project.manifest.json`

> 方法补充：涉及 OB/CB 研究设计、问卷测量、实验、多层、纵向、MI、功效、论文报告或自动解释时，必须同时读取 `27`；涉及高级 runner 时还必须读取 `18` 与 `25` 的 slice 状态。Harness 通过证明工程门禁，不自动证明方法 slice 可标为 `supported`。

## 1. 目的与适用边界

Harness 的作用是把正确的开发顺序固化成一致、可重跑、可审计的反馈回路：先确认变更边界和契约，再运行与风险直接相关的专项验证，最后使用分级门禁和机器证据收口。

本文同时规定：

1. `Quick`、`Full`、`Release` 三种模式分别证明什么。
2. 不同类型变更至少需要哪些验证。
3. 什么结果可以称为通过、未完成或失败。
4. 发布证据必须记录哪些事实。
5. 开发者、CI 和自动化代理共同遵守的工程原则。

本文不替代统计方法规格、安全审计或具体功能验收标准。相关要求仍以 `docs/02-科研方法规范.md`、`docs/06-统计验证与测试.md`、`docs/18-高级统计方法开发指南与接口规范.md` 及对应工作包为准。

## 2. 统一入口与模式契约

在仓库根目录使用 PowerShell 7 运行：

```powershell
./scripts/harness.ps1 -Mode Quick
./scripts/harness.ps1 -Mode Full
./scripts/harness.ps1 -Mode Release
```

`Full` 与 `Release` 默认以 4 个隔离 pytest worker 执行 API/R/Golden 测试，可通过 `-PytestWorkers 1..16` 显式调整；默认分发策略为 `worksteal`。覆盖率由各 worker 合并为单一报告，JUnit 与最慢测试记录写入 `output/test-performance/`。Golden case 以一案一测试项调度，验证数量、数值容差和覆盖率门槛不因并行而减少。

首次运行前应先执行 `./scripts/setup.ps1`。Harness 默认使用仓库内的 `.venv`、`.runtime/R`、锁文件和根目录 `package-lock.json`；运行产物只能写入已约定的忽略目录或明确受治理的基线路径。

### 2.1 模式矩阵

| 门禁 | Quick | Full | Release |
|---|:---:|:---:|:---:|
| 架构边界与 manifest 路径 | 必须 | 必须 | 必须 |
| Python lint 与类型债务基线 | 必须 | 必须 | 必须 |
| 前端 lint | 必须 | 必须 | 必须 |
| 生成契约漂移 | 必须 | 必须 | 必须 |
| Python/R 锁文件 | — | 必须 | 必须 |
| API、统计与覆盖率 | — | 必须 | 必须 |
| Golden 发布资格严格评估 | — | — | 必须 |
| 前端单元、E2E、可访问性、类型与构建 | — | 必须 | 必须 |
| Bundle budget | — | 必须 | 必须 |
| Python/Node 依赖漏洞审计 | — | — | 必须 |
| R 运行时基准、数值等价与资源回收 | — | — | 必须 |
| 发布证据 | — | — | 必须 |

- `Quick`：小步反馈门禁。目标是尽早发现架构、静态质量和契约漂移问题，不证明完整功能正确性。
- `Full`：合并门禁。在 Quick 所代表的约束之上，证明锁文件、API/统计、前端、覆盖率、构建和产物预算均满足当前基线。
- `Release`：发布候选门禁。在 Full 之上证明 Golden 资格、依赖审计、性能/数值等价、资源回收和发布证据完整。Golden 资格要求四类场景、双独立参考、G3 与 G5/G6、来源许可、环境 digest、多源消解、能力级突变和离线复现证据全部齐备；只有所有必需步骤实际执行并通过，版本才可称为“可发布候选”。

### 2.2 跳过参数与发布语义

`-SkipDependencyAudit` 和 `-SkipBenchmark` 只用于故障定位或受限环境中的诊断运行。使用任一跳过参数时：

1. 该运行不得被称为完整 `Release` 通过。
2. 不得以其关闭发布债务、批准发布候选或替代 CI/受控环境证据。
3. 交付说明必须明确列出未执行步骤及原因。
4. 发布证据必须记为 `incomplete`，不能被解释为正式发布批准。

当前实现已在机器层区分两者：`scripts/harness.ps1` 会把带跳过项的 Release 写为 `incomplete`，并以非零退出码结束；完整 Release 才能写为 `passed`。这仍不替代 CI 或干净工作树的正式发布审查。

## 3. 按变更风险选择验证

专项测试始终先于通用 Harness。下表规定最低要求；如果一次变更跨越多类，取各类要求的并集。

| 变更类型 | 专项验证 | Quick | 合并前 Full | 候选发布 Release |
|---|---|:---:|:---:|:---:|
| 纯文档、注释 | 链接、命令和事实核对 | 按影响 | 通常不需要 | 不需要 |
| 普通后端/前端代码 | 相关单元或组件测试 | 必须 | 必须 | 按发布计划 |
| Schema、DTO、OpenAPI、TypeScript 契约 | 生成与兼容性测试 | 必须 | 必须 | 按发布计划 |
| 统计方法或估计器 | 金标准、固定种子、边界与失败案例 | 必须 | 必须 | 必须 |
| 持久化、归档、恢复或路径处理 | 副作用前校验、身份绑定、遍历与恢复测试 | 必须 | 必须 | 必须 |
| 并发、长任务或资源管理 | 超时、取消、崩溃和资源回收测试 | 必须 | 必须 | 必须 |
| 性能优化或预算调整 | 数值等价、基准和回归阈值 | 必须 | 必须 | 必须 |
| 依赖、构建、发布或安全加固 | 锁文件、审计及相应回归 | 必须 | 必须 | 必须 |

“按影响”是指纯文档变更如果修改命令、路径、门禁定义、生成契约或发布事实，至少运行能验证该事实的最小检查；不相关的文字修订无需机械运行全部代码门禁。不能确定风险类别时，采用更严格的一类。

## 4. 结果状态与完成定义

### 4.1 Harness 运行状态

- `passed`：本模式要求的步骤全部实际执行且通过，所需证据完整。
- `failed`：至少一个已执行步骤因代码、契约、测试、预算或审计结论失败。
- `incomplete`：步骤被跳过、依赖环境缺失、运行被取消、证据缺失，或基础设施/网络故障导致无法得出工程结论。

外部网络或托管平台故障应与代码失败分开记录，但 `incomplete` 仍然不是通过。重试只能用于确认瞬时基础设施故障，不能用来掩盖可重复的测试不稳定性。

### 4.2 单个变更的完成定义

一个变更只有满足所有适用条件才算完成：

1. 范围、支持边界和不支持项已写清，没有把计划或占位实现描述成已完成能力。
2. 统计或业务决策位于正确层级，`project.manifest.json` 等机器入口按需同步。
3. 正常、边界、失败以及适用的取消/恢复路径已按风险补齐测试。
4. 涉及统计时，估计量、尺度、随机种子、金标准、provenance 和报告口径都有可复查依据。
5. 涉及持久化或归档时，路径、对象身份和资源预算校验发生在文件或数据库副作用之前。
6. 涉及性能时，有变更前基线、数值等价、资源回收和回归阈值；批准基线没有为了通过门禁而降低。
7. 已运行第 3 节要求的专项测试和 Harness 模式，结果为 `passed`。
8. 债务总账、审计报告和发布证据只引用当前提交或明确标识工作树状态下可重跑的事实。

“代码已写完”只表示 implemented。验收条件、验证和证据全部闭环后，债务项才允许标记 closed。

## 5. 发布证据契约

Release 证据不是“生成了一个 JSON 文件”，而是对本次运行事实的绑定。正式证据至少应包含：

| 类别 | 最低字段 |
|---|---|
| 来源 | commit SHA、分支、dirty 状态、运行 ID |
| 环境 | OS、Python、Node/npm、R 版本及关键硬件信息 |
| 步骤 | 步骤名称、状态、开始/结束时间、耗时、退出码 |
| 跳过项 | 是否跳过、原因、授权来源；存在必需跳过项时总状态为 `incomplete` |
| 产物 | 契约、覆盖率、bundle、审计和性能报告的路径及 SHA-256 |
| 性能 | 数据规模、重复次数、种子、并行度、数值等价、资源回收和阈值结论 |
| 汇总 | `passed`、`failed` 或 `incomplete`，以及首个失败/阻塞步骤 |

证据还必须满足：

1. 必需产物缺失时失败，不得静默省略哈希。
2. 本次运行产生的报告与历史批准基线分开保存，并能通过 commit 和运行 ID 关联。
3. dirty 工作树可以用于开发诊断，但不得直接作为正式发布批准；如确需保留，应明确标记为非发布证据。
4. 失败证据应尽可能写出已完成步骤和失败位置，但证据写入失败不能覆盖原始失败。
5. CI 与本地若使用不同步骤集合，必须使用不同的证据类型，不能都笼统称为 Release passed。

当前 `scripts/release-evidence.py` 已记录模式、运行 ID、耗时、总体状态、必需/完成/跳过/缺失步骤，以及环境和产物哈希；带跳过项会稳定归类为 `incomplete`。逐步骤开始/结束时间、退出码和完整产物清单仍是后续证据格式升级项。

## 6. 十二条工程准则

### 6.1 状态必须由证据驱动

只有验收条件逐条满足、自动测试通过且证据路径可复查，债务项才能关闭。禁止为了让总账好看而提前关闭，也禁止通过降低覆盖率、类型、bundle、性能或统计阈值绕过回归。

### 6.2 统计正确性是一等契约

每个正式方法必须同时具备明确估计量与尺度、固定种子、独立数值金标准、边界/失败案例、结果 provenance 和论文报告口径。性能优化必须先证明数值等价，不能以“更快”为理由改变估计结果。

### 6.3 能力目录必须说真话

Schema、DTO 或占位路由存在不代表方法可用。只有输入、验证、执行、结果、金标准、UI 和导出的纵向切片全部达到对应支持等级，能力目录才允许报告真实可执行状态。保留接口但没有执行器时，应明确返回不可执行状态和相应错误。

### 6.4 跨语言契约必须原子更新

JSON Schema、Python 模型、OpenAPI 和 TypeScript 类型视为一个变更单元。任何一处改变都必须重新生成并通过漂移检查；不得手工修补生成文件，也不得让兼容 barrel 再次成为业务实现入口。

### 6.5 持久化数据一律按不可信输入处理

SQLite 路径、状态 JSON、归档 manifest 和恢复数据不能因为由本机生成就被信任。文件或数据库副作用前必须完成安全相对路径、解析后 containment、准确父目录/文件名、对象身份绑定和 reparse point 拒绝等适用校验。

### 6.6 资源预算必须在分配之前生效

上传、压缩包、队列、Bootstrap、矩阵和 Worker 必须按风险设置成员数、字节、展开比、并发、超时和取消预算。先流式校验再分配内存；失败、取消、崩溃和替换后必须证明没有孤儿进程、句柄或临时目录持续增长。

### 6.7 用户状态恢复属于功能完整性

草稿、冻结版本、活动运行和结果页刷新后应恢复；“尚不存在”是正常空状态，不应制造无意义的 404 控制台噪声。长任务必须提供进度、取消、恢复和终态解释，不能只存在于当前前端 mutation 生命周期。

### 6.8 大结果必须按视口和分片交付

任务状态与正式 ResultBundle 分离，结果只保留一个权威副本；大型矩阵使用分片接口和双轴虚拟化。大规模场景应有明确的 DOM、响应体和 bundle 预算测试，具体阈值由受版本控制的基线定义。

### 6.9 性能结论必须可重复

基准记录数据规模、重复次数、硬件/运行时、固定种子、单核与并行结果、冷启动与常驻进程差异。一次肉眼变快不能关闭性能债；原始基准报告、数值等价和与同类环境基线的比较才构成证据。

### 6.10 架构边界先于实现便利

路由只翻译 HTTP，统计决策留在 service/engine；入口通过 `project.manifest.json` 可发现；大型文件和兼容入口受可复查的上限约束。Service/engine 不得反向依赖 API 或应用入口，组件文件不得因导出非组件工具破坏 Fast Refresh。

### 6.11 测试顺序要缩短故障定位

默认顺序是：阅读约束 → 确认变更类型与风险 → 最小补丁 → 专项回归 → Quick → 按生命周期运行 Full/Release。失败时修根因，不同时修改多个基线；长流程结束后显式关闭本次启动的服务器、浏览器、测试和 R Worker。

### 6.12 治理动作必须作用于正确对象

代码扫描、Codex 任务、应用页面、归档记录和操作系统进程不是同一对象。任何有歧义的“停止、关闭或清理”都应先识别对象、所有者和可逆操作，再执行最小范围动作。

## 7. 标准工作回路

1. 从 `AGENTS.md`、`project.manifest.json` 和相关规范确认入口、边界及禁止项。
2. 检查 dirty worktree，识别并保留用户已有修改，不做破坏性清理。
3. 对照第 3 节判定变更类型和最低验证集合。
4. 先读相关实现与测试，再修改一个最小、可独立验收的纵向切片。
5. 先运行最接近风险的专项测试，再运行相应 Harness。
6. 失败时记录失败步骤和类别，修复根因后从能够证明修复的最小步骤重跑；最终仍需完成要求的整个模式。
7. 更新适用的文档、债务状态和证据，清理本次启动的临时资源。
8. 最终交付明确区分：已实现、已验证、未执行、失败，以及仍需用户或外部治理的事项。

## 8. 基线、例外与变更治理

1. 覆盖率、类型债务、bundle、性能和统计容差不得仅为使当前变更通过而降低。
2. 基线调整必须作为独立、可审阅的变更，说明旧值、新值、测量方法、原因、风险和批准证据。
3. 文件行数等架构阈值属于维护性护栏，不等同于设计质量。确需例外时，应优先拆分；无法拆分时记录范围、原因、所有者和失效条件，不得静默扩大全局上限。
4. 不稳定测试必须登记并修复，不能通过无限重试或长期跳过转化成绿色门禁。
5. 新增、删除或重排门禁时，应原子更新 `scripts/harness.ps1`、`scripts/test.ps1`、CI、`project.manifest.json` 和本文模式矩阵，避免本地与 CI 语义漂移。

## 9. 不可由 Harness 自动完成的治理边界

- 首个可审计 Git 基线提交、分支保护和仓库平台规则需要明确的版本控制授权与平台配置。
- Harness 可以验证当前工作树和生成证据，但不能自行批准发布、修改平台保护规则或替代人工统计审查。
- 高级统计方法仍按 `docs/18-高级统计方法开发指南与接口规范.md` 分阶段交付，接口预留或单次运行成功不等于正式执行能力完成。
- 应用页面、Codex 任务和外部扫描的生命周期由各自所有者管理；Harness 只清理自己启动且能准确识别的进程和临时资源。

## 10. 当前实现差距与升级优先级

以下差距不改变现有门禁的价值，但在关闭前不得把证据能力描述得比实际更强；当前三项均仍开放：

1. 本地 Release 与 CI 的步骤集合不完全一致，CI 当前没有执行 R 运行时基准。
2. Quick 与 Full 的公共步骤在 `harness.ps1` 和 `test.ps1` 中存在重复，后续应改为单一门禁注册表或组合入口，避免漂移。
3. 性能原始报告、批准基线和 CI 上传产物应进一步区分，并增加 commit、运行 ID 与新鲜度校验。

建议按以上顺序升级脚本和证据格式；每项完成后同时更新本节及可重跑的验收证据。

# 28 代码—业务—文档一致性与仓库收口审计

> 审计日期：2026-07-18
> 审计类型：仓库收口、接线复核、能力诚实性与计划治理；不开发新的统计方法
> 适用版本：当前工作区及本次 Full Harness 对应代码
> 文档角色：交付时点的代码—业务—协议—测试—文档追踪与清理决定；未来产品需求仍以 `27` 为准，实时债务仍以 `debt-register.json` 为准

## 1. 结论先行

本轮完成的是“把当前项目说清楚、接清楚、删干净”，不是把路线图中的未来功能提前实现。

1. **当前代码与当前能力说明已经对齐到“有限 slice + 明确缺口”**：六个高级 family 均有 runner，`questionnaire_measurement` 已有高级 R 分发；能力名称已限缩到实际可达或明确计划的 slice。验证端点对 `experimental` 能力返回 `CAPABILITY_EXPERIMENTAL`，但 registry 的 `executionAvailable=true` 仍不能替代独立金标准、结果和方法验证。
2. **已清理具备充分证据的无用/重复代码**：一次性迁移脚本、旧式破坏性清理器、重复后端执行函数、零消费者前端 API/类型、零消费者 R 并行包装，以及复杂设计仍不可达的旧 Monte Carlo/GLMM 预留分支均已删除；当前有限 Gaussian regression/ANOVA Monte Carlo 是新接线的真实 DGP slice。
3. **已清理会误导研究结论的代码**：伪 Games–Howell、缺失效应量写 0、原始均值图冒充模型图、只为显著 omnibus 生成 APA 句子、结果页显著性星号/行高亮和错误 estimate 字段名均已收口；受限高级实验入口现使用独立 Games–Howell 实现。
4. **没有把低频代码简单当作死代码**：诊断 demo/mediation 端点、兼容 barrel、R worker、SEM helper、迁移、异常类型和生成客户端均有明确职责与消费者，继续保留。
5. **在本轮审计覆盖的受版本控制源码内，没有剩余“证据充分、可直接删除”的生产代码候选**。这不是对未来任何动态路径的数学证明，而是基于入口、导入、路由、注册表、协议、测试、基准和文档的双向追踪结论。
6. **项目规划入口已经统一**：机器事实看 manifest/Schema/OpenAPI/capability/debt register；当前规范看 `00`—`11`、`18`、`24`；OB/CB 目标与 45 个工作包看 `27`；本轮交付状态看本文。历史实现记录不再覆盖当前事实。
7. **项目仍不是“全部规划功能已完成”**：`METHOD-002` 仍是 P0；高级方法仍为 `experimental`。R2–R5 提交新增了若干真实可达的有限 runner，但没有任何一个阶段凭此自动闭合；本轮审计明确不代表 GLMM、D1-D3/复杂 pooled inference、复杂 Monte Carlo 或正式论文发布已实现。

## 2. 审计边界与判断规则

### 2.1 纳入范围

- FastAPI 应用组合、5 个领域路由、依赖 DTO 与响应 DTO；
- Python 仓储、统计编排、后台任务、导出、归档/恢复和维护服务；
- `engine/R` 的三个分析入口、常驻 worker、lib 与 SEM helper；
- React 应用入口、分域 API、类型、页面/组件、结果视图与样式；
- JSON Schema、OpenAPI 生成类型、数据库迁移与跨语言契约；
- API/前端/R/Playwright 测试、基准与工程 Harness；
- README、当前规范、历史快照、债务总账、manifest 和开发路线图。

### 2.2 不把“全文只出现一次”直接等同于死代码

代码只有同时满足下列条件才删除：

1. 不属于 manifest/OpenAPI/FastAPI router/React mount/R worker 的公开或间接入口；
2. 没有源码调用、导入、动态注册、后台任务、测试、基准或脚本消费者；
3. 不承担 JSON Schema/OpenAPI/TypeScript/Pydantic 兼容职责；
4. 不是数据库迁移、序列化兼容、异常类型、框架回调或生成文件；
5. 没有用户数据迁移、恢复、诊断或发布证据职责；
6. 存在功能等价且已接入的权威替代实现，或该代码对应的迁移已经完成；
7. 删除后由专项测试和 Harness 验证。

反过来，满足任一项的低频代码要保留并登记删除条件。异常类中的 `pass`、抽象仓储的 `NotImplementedError`、清理回调中的容错 `pass`、Pydantic 未来枚举的稳定拒绝边界，都不能仅凭文本扫描删除。

### 2.3 何谓“已接入业务”

一个模块至少通过下列一种路径获得业务身份：

```text
用户界面 → 前端 API → HTTP 路由 → service/repository → R/存储 → ResultBundle → UI/导出
                                  ↘ 后台任务/恢复/取消/审计

测试/基准 → 诊断 HTTP 或 service → 同一统计引擎/资源治理

项目升级 → migration/archive/maintenance → 受控状态目录与身份校验
```

单纯“文件存在”或“有一个 runner”不算接入；单纯“主 UI 没调用”也不自动等于无业务用途，诊断、基准、迁移和兼容消费者同样是有效业务职责。

| 对象 | 原问题 | 本轮处理 | 当前稳定语义 |
|---|---|---|---|
| `run_complex_monte_carlo()` | Python 前置校验使中介/多层请求永远无法到达；分母还只使用收敛复制 | 整段删除 | 复杂 MC 为 planned，协议稳定拒绝；未来从完整规格和验证重新实现 |

| 仅显著 omnibus APA 句子 | 强化选择性报告 | 改为对所有字段完整、可估的 omnibus 对称生成中性句子 | 不以 `p < .05` 决定是否出现 |
| 前端星号/显著行高亮 | 结果视觉由阈值主导 | 删除星号列、行高亮与 CSS | 统一展示 estimate/SE/statistic/df/p/CI |

## 6. 未清理的本地目录不属于源码残留

`.venv`、`.runtime`、`node_modules`、`.researchpath`、`.pytest-tmp`、`output` 等是依赖、用户状态或受治理产物，已由 `.gitignore`/工作区规则隔离。本轮不递归删除这些目录，原因如下：

- `.researchpath` 可能包含真实用户项目，必须通过 archive/maintenance 的身份与备份流程处理；
- `.runtime`、`.venv`、`node_modules` 是可重建依赖，但删除会改变本机环境，不是源码审计的必要动作；
- `output`、测试临时目录可能是当前验证证据，清理应由产生它们的 Harness 或明确维护命令完成；
- “交付最新项目”指受版本控制的代码、协议和文档收口，不授权扩大到用户数据或整个本机开发缓存。

## 8. 当前计划和开发计划是否清晰
